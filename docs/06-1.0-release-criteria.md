# 1.0 Release Criteria

This document defines the contract `codectx` must satisfy before declaring
`1.0.0`. It uses a conservative stable-core posture: the documented user-facing
CLI and bundle formats become stable, while ranking internals and the SQLite
database remain implementation details.

## Release Criteria

`codectx` can be declared `1.0.0` when all of the following are true:

- The pre-1.0 backlog tasks marked P0 and P1 are complete or explicitly
  deferred by a documented release decision.
- The local quality gate passes with no known release-blocking failures:
  `make ci`.
- The release workflow can build the source distribution, wheel, and versioned
  PEX artifact for a tag.
- Real-repo evaluation results are recorded for representative Java and C++
  repositories.
- README and release documentation describe the stable contract, known
  limitations, supported platforms, and artifact expectations.

## Stable CLI Contract

The following commands are part of the 1.0 stable core:

- `codectx index`
- `codectx health`
- `codectx symbols`
- `codectx search`
- `codectx context`
- `codectx neighborhood`
- `codectx inspect-node`
- `codectx inspect-edge`

The stable documented flags for these commands are:

| Command | Stable flags and arguments |
| --- | --- |
| `codectx --version` | None |
| `codectx index` | `PATH`, `--db PATH`, `--rebuild`, `--include PATTERN`, `--exclude PATTERN`, `--force-include PATTERN`, `--no-ignore-files` |
| `codectx health` | `--repo PATH`, `--db PATH`, `--integrity` |
| `codectx symbols` | `QUERY`, `--repo PATH`, `--db PATH` |
| `codectx search` | `QUERY`, `--repo PATH`, `--db PATH` |
| `codectx context` | `--repo PATH`, `--db PATH`, `--symbol QUERY`, `--file PATH`, `--line N`, `--goal explain|failure-modes|dependencies|call-neighborhood`, `--budget N`, `--format markdown|json|text`, `--output PATH` |
| `codectx neighborhood` | `--repo PATH`, `--db PATH`, `--symbol QUERY`, `--depth N`, `--direction out|in|both`, `--edge-kind KIND`, `--limit N` |
| `codectx inspect-node` | `NODE_ID`, `--repo PATH`, `--db PATH` |
| `codectx inspect-edge` | `EDGE_ID`, `--repo PATH`, `--db PATH` |

Future minor releases may add flags, output fields, context goals, and
inspection details. Removing or renaming documented commands or flags requires a
future major version or an explicit compatibility bridge.

## Stable Output Contract

The supported 1.0 context output formats are:

- `markdown`
- `json`
- `text`

Markdown and text are stable as human-readable transfer formats, not as
byte-for-byte machine contracts.

JSON is the structured 1.0 format. These top-level bundle fields and their
meanings are stable:

- `query`
- `anchor`
- `index_health`
- `items`
- `omitted`
- `uncertainty_notes`
- `trace`

The stable nested bundle fields are:

| Field | Stable nested fields |
| --- | --- |
| `query` | `goal`, `budget`, `format`, `symbol`, `file`, `line` |
| `anchor` | `file_id`, `file_path`, `line`, `node_id`, `node_kind`, `node_name`, `qualified_name`, `symbol_key`, `start_line`, `end_line` |
| `index_health` | `files`, `nodes`, `edges`, `occurrences`, `chunks`, `diagnostics`, `unresolved_references`, `feature.fts5`, and `language.<name>` counts |
| `omitted[]` | `name`, `reason`, `score` |
| `trace[]` | `stage` plus stage-specific diagnostic fields |

For each selected item, these fields and their meanings are stable:

- `rank`
- `kind`
- `file`
- `line_range`
- `text`
- `score`
- `token_estimate`
- `reason`
- `confidence`
- `extractor`
- `metadata`
- `score_trace`

The exact numeric score values, tie-break ordering, score component formula,
candidate discovery internals, and ranking trace internals are not compatibility
guarantees. Users may inspect them, but future minor releases may adjust them to
improve bundle quality.

## SQLite And Schema Contract

The SQLite database is a local cache and inspection artifact, not a public 1.0
storage compatibility contract. Users may inspect it, delete it, or rebuild it
at any time.

Future releases may require rebuilding the database after incompatible schema or
indexing changes. If a future release cannot read an existing database safely,
the tool should fail with an actionable message that tells the user to re-run
`codectx index <repo> --rebuild`.

## Runtime And Platform Contract

The 1.0 runtime baseline is Python 3.11 or newer. Project CI must continue to
cover Python 3.11 and Python 3.12 before 1.0.

Runtime dependency bounds and the parser compatibility matrix are documented in
[`dependency-compatibility.md`](dependency-compatibility.md). The CI suite must
include a smoke test that initializes the supported Tree-sitter runtime package
combination and parses minimal Java and C++ sources.

The supported release artifacts are:

- Source distribution.
- Python wheel.
- Versioned PEX attached to the GitHub Release.

PEX artifacts are built for the configured Linux and Windows CPython targets in
the release workflow. Users can also build a custom PEX locally with the
documented `make artifact` target.

## Known Limitations For 1.0

The 1.0 contract does not promise compiler-perfect analysis. The following
limitations are expected and must remain documented:

- Java and C++ extraction are Tree-sitter based heuristics.
- Java classpath, generics, annotation processing, and build-tool semantics are
  not fully resolved.
- C++ templates, macros, overload resolution, include graphs, and
  build-configuration-specific code are only partially understood.
- Call-like and reference edges may remain unresolved and must be labeled
  honestly.
- Context bundles are source-grounded prompt-preparation aids, not correctness
  proofs.

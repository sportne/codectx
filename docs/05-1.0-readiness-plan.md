# 1.0 Readiness Plan

This plan records the work believed necessary before declaring `codectx`
`1.0.0`. It does not block continued `0.x` releases.

The completed MVP backlog remains in `tasks/mvp_backlog.yaml`. The pre-1.0
task backlog is separate and lives in `tasks/1_0_backlog.yaml` so MVP history
does not get rewritten.

The 1.0 release criteria and stability contract are defined in
[`06-1.0-release-criteria.md`](06-1.0-release-criteria.md).

## Readiness Priorities

| Priority | Meaning |
| --- | --- |
| P0 | Required before 1.0. These tasks define or de-risk the release contract. |
| P1 | Required before 1.0 unless a documented release decision says otherwise. |
| P2 | Important hardening work that should be completed before 1.0 if still relevant after P0/P1 work. |
| P3 | Decision work that may produce an implementation task or an explicit deferral. |

## Detailed Tasks

### V1-001 - Define 1.0 release criteria and stable contracts

Priority: P0

Type: HITL

Status: done

Blocked by: None

Rationale:

`1.0.0` should mean that the user-facing contract is explicit. The project needs
to decide which CLI commands, JSON fields, SQLite/schema behavior, release
artifacts, and compatibility promises are stable.

Work:

- Decide which CLI commands and flags are stable for 1.0.
- Decide which JSON context bundle fields are stable for downstream tools.
- Decide the SQLite schema compatibility and migration promise.
- Decide the supported Python and platform compatibility promise.
- Record release artifact guarantees for wheels, source distributions, and PEX.

Acceptance criteria:

- Documents which CLI commands, JSON fields, schema behavior, release artifacts,
  and compatibility promises are stable for 1.0.

### V1-002 - Build real-repo context quality evaluation harness

Priority: P0

Type: AFK

Status: done

Blocked by: V1-001

Rationale:

Fixture tests prove mechanics, but 1.0 readiness depends on repeatable evidence
that generated context bundles are useful on representative real Java and C++
repositories.

Work:

- Define representative Java and C++ evaluation targets.
- Record expected useful context for each target and goal.
- Add a repeatable command or script for generating evaluation bundles.
- Record quality scores and review notes in project documentation.

Acceptance criteria:

- Adds a repeatable real-repo evaluation process with representative Java and
  C++ targets, expected useful context, and recorded quality scores.

### V1-003 - Add configurable include/exclude and ignore-file semantics

Priority: P0

Type: AFK

Status: done

Blocked by: V1-002

Rationale:

Fixed built-in ignore directories are not enough for messy real repositories,
and vendored or generated files can dominate diagnostics and context rankings.

Work:

- Design user-facing include and exclude controls for indexing.
- Define how `.gitignore`, `.ignore`, and project-specific ignore files are respected.
- Support explicitly including files that would otherwise be ignored.
- Cover subdirectory invocation and nested ignore-file behavior.

Acceptance criteria:

- Supports user-controlled include/exclude behavior, respects common ignore
  files where intended, and covers subdirectory invocation and force-include
  style cases.

### V1-004 - Improve token budgeting for large enclosing scopes

Priority: P0

Type: AFK

Status: done

Blocked by: V1-002

Rationale:

Current bundles can spend much of a small budget on required large enclosing
scopes, reducing the precision of context for real tasks.

Work:

- Identify bundle cases where target or enclosing context dominates the budget.
- Define compact fallback behavior for large required scopes.
- Preserve provenance and uncertainty notes for any abbreviated context.
- Add fixture and real-repo validation for small-budget bundles.

Acceptance criteria:

- Prevents large enclosing scopes from dominating small budgets and verifies
  budget behavior through fixtures and real-repo cases.

### V1-005 - Reduce C++ vendor diagnostics and unresolved-reference noise

Priority: P1

Type: AFK

Status: done

Blocked by: V1-003

Rationale:

Real C++ validation showed high parser diagnostic and unresolved reference
counts, especially from third-party code, which weakens context bundle precision.

Work:

- Use improved ignore semantics to reduce third-party diagnostic noise.
- Review C++ unresolved-reference patterns from real validation cases.
- Improve ranking or presentation so noisy global diagnostics do not dominate
  local failure-mode context.
- Add regression cases for the observed C++ validation failures.

Acceptance criteria:

- Reduces noisy C++ parser diagnostics and improves usefulness of C++ bundles,
  especially failure-mode bundles affected by vendored code.

### V1-006 - Pin and verify runtime dependency compatibility

Priority: P1

Type: AFK

Status: done

Blocked by: V1-001

Rationale:

1.0 should not depend on unbounded runtime parser packages whose API or grammar
behavior can change underneath users.

Work:

- Bound runtime dependencies in packaging metadata.
- Verify supported Python versions and tree-sitter package combinations in CI.
- Document the supported dependency and platform matrix.
- Add an upgrade checklist for future dependency bumps.

Acceptance criteria:

- Pins or bounds runtime dependencies and verifies supported Python/tree-sitter
  combinations in CI.

### V1-007 - Establish real-repo performance and storage gates

Priority: P1

Type: AFK

Status: done

Blocked by: V1-002

Rationale:

Synthetic performance smoke tests are useful, but 1.0 readiness needs real-repo
indexing, query, and database-size expectations.

Work:

- Define representative real-repo performance scenarios.
- Measure index time, query time, context time, and database size ratio.
- Add an opt-in or scheduled performance gate with documented thresholds.
- Record baseline results and expected variance.

Acceptance criteria:

- Defines real-repo index/query/storage thresholds and adds an opt-in or
  scheduled performance gate.

### V1-008 - Stabilize release automation and artifact publishing

Priority: P1

Type: AFK

Status: done

Blocked by: V1-001

Rationale:

1.0 releases should have repeatable tagged builds and published artifacts,
including a versioned PEX asset on GitHub Releases.

Work:

- Ensure tag-triggered release builds create or update GitHub Releases.
- Publish versioned PEX assets and workflow build artifacts.
- Document manual dispatch and recovery for existing tags.
- Verify release CI on a non-production test tag before 1.0.

Acceptance criteria:

- Ensures tagged releases create or update GitHub Releases with versioned PEX
  assets and documented manual recovery steps.

### V1-009 - Harden Unicode, encoding, and binary-file handling

Priority: P2

Type: AFK

Blocked by: V1-002

Rationale:

Source span and snippet behavior must remain correct for real-world files with
multibyte text, BOMs, invalid encodings, or binary-like content.

Work:

- Add tests for invalid UTF-8 and non-UTF-8 text files.
- Add tests for BOM handling and multibyte line boundaries.
- Decide how unsupported encodings and binary-like files are reported.
- Ensure indexing failures remain actionable diagnostics rather than crashes.

Acceptance criteria:

- Adds coverage for invalid UTF-8, BOMs, non-UTF-8 text, multibyte boundaries,
  and binary-ish source files.

### V1-010 - Simplify context planner internals without behavior drift

Priority: P2

Type: AFK

Blocked by: V1-002, V1-004

Rationale:

The context planner is the largest concentration of ranking, SQL, candidate
generation, and budget behavior; improving locality will make 1.0 maintenance
safer.

Work:

- Identify planner responsibilities that can be separated behind stable internal interfaces.
- Refactor in small slices while preserving golden output.
- Keep behavior changes gated by the real-repo evaluation harness.
- Document any intentional ranking or output differences.

Acceptance criteria:

- Refactors `context/planner.py` for locality while keeping golden and real-repo
  evaluation output stable.

### V1-011 - Document 1.0 user guarantees and known limitations

Priority: P2

Type: AFK

Blocked by: V1-001, V1-002, V1-006

Rationale:

Users need clear 1.0 documentation for what is stable, what remains heuristic,
what platforms are supported, and how future migrations will be handled.

Work:

- Update README and release-readiness docs with 1.0 guarantees.
- Document supported platforms, Python versions, and artifact types.
- Document known Java and C++ heuristic limitations.
- Document migration expectations for future schema or output changes.

Acceptance criteria:

- Updates README/docs to clearly state 1.0 guarantees, caveats, supported
  platforms, and migration expectations.

### V1-012 - Decide whether incremental indexing belongs before 1.0

Priority: P3

Type: HITL

Blocked by: V1-007

Rationale:

Incremental indexing may improve repeated real-repo workflows, but it also adds
complexity and compatibility surface that may not be needed for 1.0.

Work:

- Use real-repo performance evidence to decide whether full reindexing is acceptable for 1.0.
- If needed, define the minimum incremental indexing behavior for 1.0.
- If deferred, record the rationale and expected future trigger.
- Update release criteria and documentation with the decision.

Acceptance criteria:

- Records a decision on incremental indexing before 1.0, either implementing a
  minimal version or explicitly deferring it.
